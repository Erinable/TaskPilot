# Repository Guidelines

## Project Structure & Module Organization

TaskPilot is an Electron app built with electron-vite: TypeScript in the main process and preload, Vue 3 + Pinia + Element Plus + UnoCSS in the renderer.

- Main-process domains: `app/` assembles shared application state and run lifecycles; `infrastructure/` owns errors, logging, environment and persistence; `repository/` owns git, workspace and repository configuration; `checking/` owns verification and `checking/presets/`; `runtimes/` owns CLI protocols, native configuration and isolation setup; `coding/`, `work_packages/`, `requirements/`, `courses/`, `notes/`, `activity/` and `release/` own their business flows. Only `index.ts` and the IPC assembler stay at the main root. Unit tests mirror these directories; IPC integration tests share `tests/main/ipc/harness.ts`.
- Cross-process state: `src/shared/ipc/state.ts` declares `state:changed` invalidations containing only repository identity and changed domains. Stores emit after committed writes (including external note edits), runs emit progress, and `infrastructure/state_changes.ts` coalesces bursts without relabeling old-repository events. Renderer stores fetch initially and subscribe while active; dispose listeners on leave/reset, serialize refreshes, and reject stale responses. `stores/repository_identity.ts` holds identity without importing the switch orchestrator. Timers are only for real debounce, elapsed display, or process deadlines—not state refresh.
- Errors and logs: `src/shared/error_codes.ts` is the closed application-code vocabulary; `coded_error.ts` and the IPC boundary normalize external failures to `unknown`. Main code uses `infrastructure/logger.ts`, default level `info`, writing `userData/logs/taskpilot.log` with 0600 permissions and flushing on quit. Logging failures never fail the business action.
- Storage: `infrastructure/persisted_json.ts` accepts an absent format version as v1 and rejects unsupported versions before reads or replacements, including saves without a prior load. Array/map stores use versioned envelopes; workspace remains v3 and course trust v2. Activity JSONL uses `storageVersion` (release events already have a semantic `version`). `JsonWriteQueue.enqueue()` keeps guarded writes serialized and included in `flush()`. Newer files must not be cleared by reset, directory changes, or lab replacement. Third-party CLI configuration and user Markdown/course content keep their own formats.
- Large-module boundaries: note validation/frontmatter lives in `notes/note_file.ts`, package recovery/transition rules in `work_packages/work_package_state.ts`, coding protocol parsing in `coding/coding_protocol.ts`, and tool-less JSONL validation in `runtimes/structured_output.ts`. Lab artifact, draft IO, planning, estimation and renderer-safe projections live beside the lab service. Services declare a `Pick<AppContext, ...>` of the capabilities they actually need; do not widen them for convenience.
- Renderer boundaries: settings owns authoritative drafts while `settings_agents.ts` handles CLI catalogs/runtime state; `AgentsPage.vue` composes `AgentConfigRow.vue` and `AgentModelPicker.vue`. `CodingPanel.vue` composes patch review, transcript, round history and checks. Execution and course requirement actions use explicit ref dependencies in `execution_actions.ts` and `requirements_course.ts`.
- Tests assert behavior, boundaries and transitions. Do not restore prompt golden files or source/implementation snapshots; intentional prompt changes are checked with the existing model evals. Retain security guards for unsafe markup, CSP and Electron's CommonJS shim markers.
- `src/main/index.ts` — main process: window creation and IPC registration. In dev it loads the electron-vite dev server, otherwise `out/renderer/index.html`.
- `src/main/infrastructure/env.ts` — the only reader of `process.env` in the main process.
- `src/main/ipc.ts` — assembles the IPC layer; testable with a fake `ipcMain`. Each domain registers its channels in `src/main/ipc/<domain>.ts` (`register(ipcMain, ctx, services)`), which only validates arguments and routes. Shared state (stores, config, preferences, the background run registry, `record`/`recordCall`) lives in `src/main/app/app_context.ts`; longer flows live in IPC-free services: `coding_service.ts` (the Coding Agent loop, over `coding_runtime.ts`), `review_service.ts` (QA, Architect's ruling, the baseline), `requirement_service.ts` (Product Lead clarification and planning), `practice_service.ts` (reference and grade) and `release_service.ts` (Release Manager drafting and notes). Tests mirror this under `tests/main/ipc/`, sharing `tests/main/ipc/harness.ts`: they wait for background runs with `h.idle()` (`IpcHandle.idle`, which waits without cancelling and flushes the stores) and poll only through `until()` (`tests/fixtures/until.ts`), for a phase a held run stops in.
- `src/main/app/background_runs.ts` — the registry of background runs. Every run that outlives its IPC call registers its controller and promise here; cancelling on a switch, reset or quit, the switch dialog's busy list and the team's busy work are all read from it, so a new kind of run only needs to register.
- `src/shared/ipc/<domain>.ts` / `src/shared/ipc_channels.ts` — the typed wire contract shared by main, preload and renderer, plus `envelope.ts` (`IpcResult`, `ErrorInfo`); `coding_types.ts` and `agent_runtime.ts` hold the coding and agent types. Every channel is declared once in a contract table (`commitContract = { preview: invoke<[id: string], CommitPreview>('commit:preview') }`, helpers in `ipc/contract.ts`) listed in `ipc/contracts.ts`: the preload builds every namespace from the tables, `index.d.ts` derives `TaskPilotApi`, main registers each invoke with `registerContract` (`src/main/ipc/handler.ts`, which type-checks results and rejects missing or extra handlers), and `CHANNELS` derives its keys (namespace + capitalized method). Adding a channel is one table entry and one handler; never duplicate it in preload or `ipc_channels.ts`. Startup and full-screen events are under `app`, task reads under `tasks`, and work-package mutations under `packages`. Existing wire channel strings stay unchanged. `src/shared` must not import from `src/main` (ESLint).
- `src/preload/index.ts` — exposes `window.taskpilot` (typed as `TaskPilotApi`) via `contextBridge`. It is bundled to CommonJS (`out/preload/index.cjs`) because sandboxed preloads cannot be ES modules.
- `src/main/work_packages/tasks.ts` — the work-package definition types and the `TaskCatalog` interface. `RequirementStore` is the catalog: it serves the packages published from requirements as frozen, shared objects. Tests publish `tests/main/fixtures/sample_tasks.ts` through `SAMPLE_REQUIREMENT`.
- `src/main/activity/activity_log.ts` — append-only activity events, one JSONL file per business day under the repository's `events/`, kept 30 days and pruned at startup. `app_context.ts` records every package transition and requirement outcome; the queue's metrics, the activity feed, team presence and weekly spend are computed from it (`activity:overview`), served from an in-memory summary (`src/main/activity/activity_summary.ts`) that is built from the window once per opened repository and updated by every append. A failed append is logged and never fails the action; `activity:page` serves the full feed a few business days at a time. Day boundaries follow `env.businessTimeZone` (`TASKPILOT_TIME_ZONE`, default `Asia/Shanghai`), the single business time zone: the preload passes it to the renderer as `window.taskpilot.businessTimeZone`, read through `src/renderer/src/lib/time_zone.ts`.
- `src/main/repository/engineering_map.ts` — the engineering map: Architect's module summaries from every requirement merged by file (newest wins), each marked stale when the file's blob changed since it was read, beside the tracked file tree (capped at 5000 paths). It never calls a model.
- `src/renderer/src/` — the Vue app: `App.vue`, `views/` (one per top-level view), `components/`, `stores/` (Pinia setup stores), `lib/` (pure logic and IPC helpers). Components and views read stores and never call `window.taskpilot` (ESLint enforces it); state a view reads for one repository lives in a store that `stores/repositories.ts` resets on a switch. Agent-written text is rendered with `{{ }}` only, never `v-html`. The page has a strict CSP (`script-src 'self'`, `style-src 'self'` in production).
- `src/renderer/src/lib/icons.ts` + `components/AppIcon.vue` — the SVG icon set. `IconName` is typed, so vue-tsc rejects unknown names; `tests/renderer/lib/icons.test.ts` also checks names in data.
- `src/renderer/src/stores/settings.ts` — settings state; `lib/settings_model.ts` holds its pure logic (dirty tracking, search). New settings pages need a nav entry in `SettingsView.vue`, a page component under `components/settings/`, and an entry in `PAGE_STORES`.
- `src/main/agents/` — the AI team. Each agent sees only its layer:
  - `architect.ts` reads code (through `src/main/repository/repo_reader.ts`) and publishes a module interface summary;
  - `product_lead.ts` plans from the summary and the file list, and never sees source code;
  - `qa.ts` reviews a submitted package against its steps, scope and acceptance criteria. `decide()` combines the model's verdict with TaskPilot's own evidence: a failing blocking check or a failed/missing linked test rejects regardless of the model, and the model can only make a review stricter;
  - `env_steward.ts` (Environment Steward) reads the facts `presets/typescript_setup.ts` gathers and picks an install mode and existing `package.json` script names. It never writes a command, and its suggested fixes are shown to the user but never run;
  - `release_manager.ts` (Release Manager) drafts a version bump, release notes and a pre-release checklist from the commit subjects, changed paths (no contents) and finished packages since the last release. Release Manager never tags, commits, pushes or runs release commands; its one repository write is inserting the notes into a `.md` file the user names (`release:write-notes`, path-checked). Releases and the draft live in the repository's `releases.json` (`src/main/release/release_store.ts`);
  - `pipeline.ts` runs Architect's steps, QA's review, the steward's plan and the release draft; `claude_cli.ts` runs the isolated, tool-less CLI.

  All model output is validated before use. Agent prompt changes should be checked with `npm run eval:product-lead -- --architect`, `npm run eval:qa`, `npm run eval:architect` or `npm run eval:tutor-grade` (see the README in each `evals/` directory).
- `src/main/repository/repo_reader.ts` — the only source of file contents for agents. It reads from git blobs, only tracked files, and refuses secret-looking paths. Any agent that needs code goes through it.
- `src/main/repository/review_diff.ts` — the only source of working-tree diffs for QA. It reads only paths git reports as changed since the baseline (untracked included), refuses secret-looking paths with the same patterns as `repo_reader.ts`, skips binaries, caps sizes, and reports every skipped file.
- `src/main/checking/presets/` — language presets (`preset.ts` is the interface: detect, default steps with parsers, command suggestions, required tools). `typescript.ts` maps npm scripts onto steps; `rust.ts` runs Cargo over the whole workspace (clippy / build as Cargo JSON diagnostics, rustfmt diff headers, `cargo test` or, when `cargo-nextest` is on the command PATH, nextest's libtest JSON), checked end to end on `tests/main/fixtures/rust_sample` with parsers tested on the real outputs in `tests/main/fixtures/rust_output`; `python.ts` sets up `.venv` with `uv sync --locked` (only with a tracked `uv.lock`, otherwise `uv venv` + `uv pip install`) or, without uv on the command PATH, `python3 -m venv` + pip, then runs Ruff (format, `check --no-fix` JSON), Pyright when it is on the PATH or in `.venv` else mypy (JSON), and pytest with a JUnit report in `.taskpilot/reports/`; it is checked end to end both ways on `tests/main/fixtures/python_sample`, parsers on `tests/main/fixtures/python_output`; `typescript_setup.ts` is Node/npm environment setup: it probes tracked manifests, lockfiles, version pins and CI workflows, and builds every setup command from fixed npm options plus validated script names (`--ignore-scripts` unless the user allows lifecycle scripts). Packages the npm lockfile marks `hasInstallScript` (not optional) get a separate `npm rebuild <names>` step, so only they run scripts. The renderer only sends a step id; `ipc/environment.ts` rebuilds the command from the stored plan and runs it after the user's click. A missing tool is only reported with its install command, never installed.
- Check steps — reviews, the coding loop and grading only know the fixed steps `setup / build / format / lint / typecheck / test / coverage` plus `custom:<name>` (`src/shared/check_steps.ts`). `src/main/checking/effective_steps.ts` merges each step field by field from the preset named in the repository's `taskpilot.toml` (`project_config.ts`, validated with field-named errors), the file's own `[steps.*]` / `[custom.*]`, and this machine's `workspace.json` (v3 `steps`; v1/v2 checks are upgraded on load, `smoke` becomes `custom:smoke`). Without `taskpilot.toml` there is no preset, so only local steps run. `step_config.ts` validates every step; `verification.runStep()` runs a step's commands in order (execFile, no shell) and `check_output.ts` turns tests / JUnit / JSON (ESLint, TaskPilot's own) / SARIF / regex / exit-code output into one `{file, line, column, severity, message, rule}` diagnostic list. `taskpilot.toml` is a high-risk path for Coding Agent patches.
- Course packs — `src/shared/course_pack.ts` holds the `CoursePack` / `CourseRef` types and `DEFAULT_COURSE_ID` (`programming`). The built-in packs, `programming` and `os`, are files in `resources/courses/<id>.toml`, copied into the app bundle's `Resources/courses` (electron-builder `extraResources`) and read once at startup by `courses.loadBuiltinCourses()` (a broken one fails startup); the main process passes them around as `ctx.builtinCourses`, the renderer gets the default pack from `courses:default` (`stores/courses.ts` `defaultPack`), and tests load them through `tests/fixtures/builtin_courses.ts`. `src/main/courses/course_file.ts` parses and validates a pack file with field-named errors (`rubric[1].dimension`), including length caps, no control characters and no prompt tags; the rules themselves are `src/shared/course_rules.ts` (`checkCourse` lists every error), so the renderer's pack editor shows the same errors on the same fields, and the main process checks again on every read and save. `src/main/courses/courses.ts` picks the pack: this machine's `workspace.json` `course`, then `taskpilot.toml` `course`, else `programming`. A pack is built in, `.taskpilot/courses/<id>.toml` in the repository, or imported into the global folder `userData/courses/<id>.toml`; a repository file wins over an imported one of the same id, neither can replace a built-in id, and built-in packs need no confirmation. A repository or imported pack is only used after this machine confirms its content hash (`course_trust.json`: the repository's data directory for its packs, userData for imported ones; `workspace:confirm-course`); until then, and when the choice is unknown or broken, `programming` is used. The confirmation keeps the content confirmed, so a changed pack lists its changed fields (`src/shared/course_changes.ts`). The sidebar view 课程 (`views/CourseView.vue`, `components/courses/`, `stores/courses.ts`, `ipc/courses.ts`) lists every pack by source with the one in use, shows a pack's whole content (`CourseContent.vue`, shared with `CoursePreviewDialog.vue`), picks one for the repository (`courses:select`, workspace.json `course`), copies any pack into the global folder under a new id (`courses:copy`), and edits imported or copied packs in a form (`CourseEditor.vue`, `courses:save`, which writes the TOML from the validated content); built-in packs are read-only. A copy or a save is a `user` pack with a new content hash, so it is pending until confirmed. The settings page 课程包 (`components/settings/CoursesPage.vue`) keeps the pack in use and where the choice came from, the packs waiting for confirmation (previewed in full first), and importing a file by validating it (`courses:pick-import`, native file dialog) and copying the content shown (`courses:import`); importing, copying and saving never confirm. Both warn when `appliesTo.languages` names none of the repository's languages. `.taskpilot/courses/**` is a high-risk path for Coding Agent patches, and only `.taskpilot/courses/` under `.taskpilot/` is tracked by git. The callers in `ipc/requirements.ts`, `ipc/tutor.ts` and `practice_service.ts` pass the pack in use (`ctx.course()`) to Product Lead (`systemPrompt(course)`, `planPrompt({ course })`: learner, difficulty and mode guides), Tutor's step explanation (`systemPrompt(course)`: `tutorGuide`) and the reference run (`referenceGuide`); a plan records the pack's `CourseRef` and its published packages carry it as `course` (absent before packs were read: programming). Grading marks along the pack's rubric and snapshots it on the grade. Changes to a built-in pack are checked with `npm run eval:tutor-grade` and `npm run eval:product-lead -- --course <id>`. `src/main/agents/` never imports the loader, presets, `project_config.ts` or TOML (ESLint `no-restricted-imports`).
- Course labs — `src/main/courses/labs.ts` says what a lab is (`LabArtifact`) and checks one before anything is written (`checkLab`: starter files stay inside the repository and out of TaskPilot's own paths, public tests are `tests/public/NN_*.sh` for stage NN, sizes are capped). A lab repository is staged: lab N is stage N, `make grade` (TaskPilot's `Makefile`, `tests/grade.sh`, the lab's `tests/build.mk`) runs every stage's public tests so far, and `taskpilot.toml` names `course`, a `custom:grade` submit step and the `[[labs]]` list (`project_config.ts`; files without `labs` read as before). The student's path is `.taskpilot/course_plan.toml`, the only other tracked file under `.taskpilot/`. A lab's private parts (`reference.patch`, `hidden/`, `hints.json`, `verify.json`) live in `userData/repos/<id>/labs/<labId>/`, outside the repository, so they are never in its git or in a Coding Agent run directory (a `git archive` of the baseline), and no channel returns them. `src/main/courses/lab_service.ts` creates a lab repository in an empty folder (`git init`, write, first commit through `git_commit.ts`, `repositories.add`, open it like a switch via `ctx.openRepository`) and adds the next stage to the open one (new files plus a `[[labs]]` table appended to `taskpilot.toml`, refused while `taskpilot.toml` or `tests/build.mk` has uncommitted changes). TaskPilot writes and commits these files itself because `tests/`, `Makefile` and `taskpilot.toml` are high-risk paths for Coding Agent patches. Each lab is published under the requirement `course-labs` (`RequirementStore.publishPackages`) as a practice package `lab-<id>` carrying `lab` and `concepts`, each stage depending on the one before. Claiming a lab starts no reference run: `practice_service.ts` marks the lab's own reference ready (`source: 'lab'`). At review, `src/main/courses/lab_hidden.ts` copies the working tree (git's files, no secret-looking ones, its own `tests/public/` left out) into a scratch folder with TaskPilot's `Makefile` and `tests/grade.sh` and the lab's private `hidden/` as the tests, and runs `make grade` with the self-check's sandboxed grader; the result is one more blocking check, `custom:hidden-tests`, passed to `reviewWorkPackage` as `extra` evidence (no baseline), so a failing hidden test rejects like a failing public one. Only test names and pass/fail are kept: no output, and no script reaches QA, Tutor or the renderer. A grader that cannot run (no Seatbelt) leaves it unverifiable. The service is reached from the main process only (`IpcHandle.labs`), since a lab carries its private parts; tests drive it with `tests/main/fixtures/sched_lab.ts`.
- Lab generation — once a course path is confirmed, `src/main/courses/lab_generation_service.ts` generates its first lab (the first concept still to learn; easy unless the form says the learner is solid). `requirements:lab-estimate` names the concepts and prices the two calls from the synced price table without running anything; `requirements:lab-generate` starts the run after the learner's click, registered like an interview run (`requirements:cancel`, cancelled by a switch), its progress and spend on the requirement's `course.lab` (title and counts only). The generator, `src/main/agents/lab_generator.ts`, has no tools and returns JSON in two calls: the statement, build rules, public and hidden tests (spec), then the starter, the solution and the L1–L5 hint ladder (code); `repair` rewrites only the parts a failed check names (for T5). Validation covers paths (under `src/`, no `..`, not secret-looking, not already in the repository), `NN_<name>.sh` test files, test names (printed by the script, unique, shell-safe; a hidden test's name has no digits or `=`/`->`/`→`), acceptance linked to public tests, both `build`/`clean` targets, sizes, and hint code (none at L1–L3, at most 3 / 10 lines at L4 / L5, else dropped). The draft (`userData/lab_drafts/<requirementId>/lab.json`, 0600) holds the private parts and is read by the main process only (`IpcHandle.labGeneration`); `toLabArtifact` makes the reference patch from the starter and the solution with `git diff --no-index` (`git.diffFolders`) and checks the result with `checkLab`. Prompt changes are checked with `npm run eval:lab-gen` (`evals/lab-gen/README.md`).
- Lab self-check — the same run then checks the draft (`src/main/courses/lab_verify.ts`, phase `verify`): `make grade` on TaskPilot's scaffolding plus the lab in a scratch folder, under the Coding Agent's Seatbelt profile with the network denied (`buildProfile({ offline: true })`) and an empty environment; without Seatbelt it refuses (`sandbox_unavailable`), never runs model code unsandboxed. Four checks: the solution passes every public, hidden and earlier-stage test; the starter builds, fails every public test of its stage and passes the earlier ones; of five mutants (`src/main/agents/lab_verifier.ts`, exact `find`/`replace` edits to the solution) all tests catch at least 4 and the public tests alone at least 2, a mutant that does not build counting as not caught; and a separate review with its own prompt finds no `untested_requirement` / `unfounded_test` / `outside_interface` issue. A failed round's report goes to the generator's `repair` with only the parts the failures name (phase `repair`), at most twice; still failing, the lab is `needs_review` and the 课程 interview offers another concept still to learn on the path (`requirements:lab-estimate` / `lab-generate` take an optional `conceptId`). Every call is a Tutor call on the requirement, so it is on the cost page and in the cost rollup. The report (`verify.json` beside the draft, then the lab's private `verify.json`) holds test names, mutants and issues; the requirement's `course.lab.verify` carries only verdicts and counts. Tests replace the grader through `IpcDeps.labGrader`.
- Lab repository and stage bar — a lab whose self-check passed is written with `requirements:lab-place` (`lab_generation_service.ts` `place`): the first one creates the lab repository in an empty folder the learner picks (`lab_service.createRepository`, which switches to it; the renderer goes through `stores/repositories.ts` `placeLab` like any switch) and copies the course requirement there (`RequirementStore.putCourse`), leaving the one where the interview ran pointing at it (`course.repositoryId`); later ones are the open repository's next stage (`addLab`). The next lab is generated only in its lab repository, once the last stage is done and the ready one is written (`previous_lab_open`, `lab_not_placed`), as stage N + 1 against the repository's labs, `src/` files and `tests/build.mk`, and its self-check runs on top of the working tree with the earlier stages' public tests (`lab_hidden.workingTree`). `LabGeneration.stage` / `placed` say where it stands. In a lab repository the queue shows the stage bar (`components/queue/LabStages.vue`, `lib/lab_stages.ts`): each lab locked / in progress / passed / waiting for review, the next one while generating (progress, spend, cancel) or ready to write, and 生成下一个 lab once every stage passed.
- Course interview — "我想学…" (requirement center, and the 课程 view's button) makes a course requirement (`kind: 'course'`) on the same state machine and channels as a project; `ipc/requirements.ts` routes it to `src/main/requirements/course_interview_service.ts`, and project requirements are untouched. The learner picks level, target, environment and weekly time (`GoalForm`, `src/shared/course_plan.ts`); Tutor (`src/main/agents/course_interview.ts`) picks one of the packs this machine trusts that has concepts, or none, and asks at most 3 questions (clarifying → answering). The learner picks a pack or 新建课程包: planning either plans a path through the pack's skeleton (in prerequisite order, at most 3 `ai:` extra concepts; `CoursePlan` with its `GoalProfile`, stored on the requirement until the lab repository exists) or drafts a whole pack, validated with `checkCourse` and retried once with the errors. In reviewing the learner marks path entries 已会 / 跳过 and reorders them within the prerequisites (`requirements:course-path`); confirming the path is `requirements:publish` and adds nothing to the queue. A draft is shown in full, edited in `CourseEditor.vue`, saved into `userData/courses/` (`requirements:course-save-draft`, a `user` pack, pending) and confirmed at the content shown (`requirements:course-confirm-draft`) before a path is planned from it.
- Mastery — `src/main/courses/mastery_store.ts`, global in `userData/mastery.json` (`JsonWriteQueue`): one `MasteryRecord` per (course, concept) with its last 20 attempts (`{ at, packageId, repoId, result, independence, errorTypes }`), totals over every attempt and the top 10 error types. `practice_service.ts` writes one attempt per concept of the package once its grade is done, only for practised packages with `concepts`, once per (repository, package, diffDigest); a failed write is logged and the grade stands. `result` is pass (every test passed, `practice.testsPassed`, and QA accepted), partial (more than half the blocking checks' tests passed) or fail. `errorTypes` are the grade comments' rubric categories plus Tutor's `errorTags` (kebab-case, at most 3; a malformed one is dropped). `independence` is the grade's independence score (null on attempts from before scores). Project packages get concepts from Product Lead: with a pack that has a skeleton, the plan prompt lists its ids and `planSchema(course)` adds `concepts` (enum, at most 3); `validatePlan` keeps only skeleton ids and drops a longer list whole. A pack without a skeleton (programming) plans exactly as before. A note saved from a grade comment carries the package's `concepts` in its frontmatter. Each attempt also keeps the package's difficulty and the highest hint level opened.
- Practice scores — a done grade carries `scores` (`src/main/work_packages/grade_scores.ts`, pure): quality 0–100 (tests and linked acceptance criteria 40 by the share passed, QA accepted 20, the rubric 40 from Tutor's `levels`, 1–4 per rubric item, which `gradeSchema` requires and `validateGrade` checks) and independence 0–100 (100 less L3 5 / L4 10 / L5 20, each level once; 40 when the reference was first read through the hint ladder before the tests all passed, kept as `ReferenceRun.revealedWith`; 30 × the share of the submission's added lines in runs of 3+ lines matching shown code, `hint_leak.copiedShare` over the opened levels' snippets and the read reference; never below 0), with every signal, so the panel (`GradeScores.vue`) shows each deduction. The model gives only the levels. After a grade made with the reference, once it is unlocked, `src/main/work_packages/explanation_service.ts` (`explain:start` / `explain:answer` / `explain:save-note`, run kind `explain`) has Tutor pick at most 3 differences (`differencesPrompt`), takes one answer per difference (null skips), gets one reply per answer (`feedbackPrompt`), and saves one note with the package's concepts, the grade's course and the most common category; it lives on `Grade.explanation`, counts towards neither score and only records `completed`. Grades from before have neither field and show as before.
- Next lab and review — `src/main/courses/lab_progress.ts` holds the pure rules. A concept is mastered when its last two attempts passed with independence of at least 70 (null independence does not hold it back). The next lab (`lab_generation_service.ts` `nextLab`, behind `requirements:lab-estimate` / `lab-generate`) covers the first planned, not mastered concept on the path whose prerequisites all passed (off the path, known or skipped counts as passed), preferring one whose last attempt did not pass. Its difficulty follows that concept's last attempt (or the path's latest one, else the form's level): two fails lower it one level, a pass with hints up to L2 raises it, anything else keeps it. Two fails at easy make it `stuck`: the estimate lists the concept's notes and `requirements:course-skip` marks it skipped. Notes that carry concepts are reviewed on the Leitner intervals 1 / 3 / 7 / 14 / 30 days (`mastery:reviews`, `mastery:review`): remembered moves up a box, forgotten goes back to box 1, and a note is only reviewable once due. `dueDay` is a business day in `env.businessTimeZone`; schedules are kept in `mastery.json` `reviews`, one per note, dropped once the note is gone.
- Mastery page — the sidebar view 掌握度 beside the notes (`views/MasteryView.vue`, `stores/mastery.ts`, `lib/mastery_model.ts`): one pack's concept skeleton as a mermaid graph coloured by state (未开始 / 学习中 / 通过过 / 已掌握, `lab_progress.conceptState`), the notes due today with 记得 / 不记得 (`mastery:reviews` / `mastery:review`) and the pack's top 5 error types. A concept lists its attempts (YYYY-MM-DD HH:mm:ss in the business time zone), its notes in that pack, and the open repository's labs and project tasks that carry it. `mastery:course` (`lab_progress.courseMastery`) serves the skeleton with each concept's standing and the pack's registered lab repositories (their `taskpilot.toml` names the pack and lists labs); the 课程 view shows those repositories and the counts by state for the pack it shows.
- Practice reference — a ready reference opens once the package's tests all passed in a finished review (every blocking check passed, every linked acceptance test verified; QA's own verdict does not count) or the hint ladder was used up to L5, and stays open once read. The rule is `practice.referenceLock()`, the same for course labs and project practice packages; `practice_service.ts` `revealReference` enforces it (`reference_locked`) and the task view carries it as `referenceLock`. Until T7's hint ladder exists `practice.usedHintLevel()` is always null, so only the tests open it.
- `src/main/checking/evidence.ts` — pure rules that turn check runs into `pass / fail / unverifiable` evidence, comparing against the baseline measured when a package is claimed (clean tree only, in the background; see `measureBaseline` in `review_service.ts`). Failures already present at the baseline do not reject; unverifiable evidence never rejects but is listed as `attention` for the human at acceptance. Its decision table is tested row by row in `tests/main/checking/evidence.test.ts`.
- `src/main/app/preferences.ts` / `src/main/infrastructure/shell_env.ts` — per-machine preferences and the login-shell PATH lookup used by verification commands.
- `src/main/repository/git_commit.ts` — the only code that writes git history: `commit:create` commits an accepted package's uncommitted files inside its file scope, after the developer reviews the list and message. It recomputes the list and refuses if it changed, never passes `--no-verify`, never pushes, amends or switches branches; secret-looking and out-of-scope files are listed and left for the developer. `src/main/repository/git.ts` stays read-only.
- `src/main/agents/tutor.ts` / `src/main/work_packages/tutor_store.ts` — Tutor explains one step to a beginner on request (`tutor:ask`), from the package's scope files as committed (read through `repo_reader.ts`). No tools, validated output rendered as text; answers are cached per step in the repository's `tutor.json` and keyed on the step's text, so a replan invalidates them.
- `src/main/notes/note_store.ts` — learning notes, global: a folder of Markdown files (default `userData/notes/`, or a folder the user picks, e.g. an Obsidian vault). Title = file name; TaskPilot's fields live in YAML frontmatter, other fields are kept. A watcher picks up outside edits and a save refuses to overwrite a changed file unless forced. `src/shared/note_markdown.ts` finds `[[links]]`, `#tags` and headings (never inside code) for both processes; `components/notes/NoteMarkdown.vue` renders the syntax tree as Vue nodes, never HTML. Grading reads each note's title and summary (`notes:summarize`, on request), not the body. A note's `category` is a rubric item id of its pack's rubric and `course` names the pack (absent: programming); both are kept as written even when unknown, and a save only writes them when they change. `src/shared/note_courses.ts` maps a note onto its rubric item and shared dimension; the notes page (`notes:courses`) filters and counts by the rubric of the pack in use or by thinking / writing / style across packs, and grading (`practice.notesForGrade`) reads notes on the changed files, then the pack in use's, then other packs' on a dimension its rubric has.
- `src/main/repository/repositories.ts` — the repository registry (`userData/repositories.json`). Each repository, identified by its git top-level path, keeps its own `workspace.json`, requirements, work package state, releases and events in `userData/repos/<id>/`; preferences stay global. Files from before repositories move there once at startup, after a copy to `userData/backup-before-repositories/`. A switch (`repositories:switch` in `ipc/repositories.ts`) cancels every background run, waits for its writes, then reopens the stores in order (requirements, whose published packages are the task catalog, then work packages); the renderer asks before cancelling (`stores/repositories.ts`) and remounts the views.
- `src/renderer/src/assets/styles.css` — frosted-glass theme. Surfaces use the `.glass` / `.glass-strong` classes and the CSS variables at the top; light and dark follow the system. `element_theme.css` maps Element Plus variables onto it.
- Main-process source must not contain the text `require(`, `__dirname` or `__filename`: electron-vite then injects a CommonJS shim that can land inside a string literal (guarded by `tests/migration.test.ts`).

Keep automated tests under `tests/`, static files under `assets/`, and scripts under `scripts/`. Mirror the `src/` layout in `tests/`.

## Build, Test, and Development Commands

- `npm install` — install dependencies.
- `npm run dev` — electron-vite dev server with hot reload.
- `npm run build` — bundle main, preload and renderer into `out/`.
- `npm start` — run the built app (`electron-vite preview`).
- `npm test` — run `tests/**/*.test.ts` with Vitest. Component tests opt into a DOM with `// @vitest-environment happy-dom`.
- `npm run test:fast` — the same without the `e2e` tier, for local runs; CI runs `npm test`.
- `npm run typecheck` — vue-tsc over main, preload, renderer and tests.
- `npm run lint` — ESLint (`eslint.config.ts`): checks the conventions below that a tool can (const arrow functions, // comments, inline exports, no `v-html`/`innerHTML`, `process.env` only in `src/main/infrastructure/env.ts`, no explicit `any`).
- `npm run format` / `npm run format:check` — Prettier (`.prettierrc.json`). The one-time formatting commit is listed in `.git-blame-ignore-revs`.
- `npm run eval:product-lead` / `eval:qa` / `eval:architect` / `eval:tutor-grade` / `eval:lab-gen` — eval harnesses for Product Lead, QA, Architect, Tutor's grading and the lab generator (real model calls, cost money); Node runs the `.ts` files directly.

CI (`.github/workflows/ci.yml`) runs typecheck, lint, format:check, test and build on Ubuntu and macOS, with uv, Rust, cc and make installed at pinned versions; its `analyze` job fails when jscpd's duplication exceeds the `.jscpd.json` threshold (1%). Do not introduce duplicate commands that bypass these scripts.

## Coding Style & Naming Conventions

Stack: electron-vite + TypeScript + Vue 3 + Pinia + Element Plus + UnoCSS, tested with Vitest. All source is TypeScript or Vue.

- Indent with two spaces (JS, TS, Vue, JSON, YAML, Markdown).
- File and directory names are lowercase joined with underscores, for example work_package_store.ts. Vue components are PascalCase .vue files. Project imports carry their full suffix (.ts, .vue).
- camelCase for variables and functions, PascalCase for classes, types and Vue components.
- Spell names out in full (groupId, not gid). Loop variables use the singular of the collection (for (const row of rows)); short names only in one-line lambdas.
- Define functions with const arrow functions, not function declarations. Return in one line when the body is one expression.
- Comments use // only.
- Export inline where a symbol is defined; no aggregated export { a, b } at the end of a file.
- Library imports first, project imports below, one blank line between. More than three imports from one project module use a namespace import (import * as store from './work_package_store').
- Internal config that is missing throws; do not paper over it with || defaults. Defaults with || are for external input only.
- No (x as any).prop = value to get around types.
- process.env is read in one config module only; everything else imports from it.
- No over-abstraction: one-off logic stays inline instead of becoming a helper. Prefer small modules with descriptive names over catch-all files.
- Renderer templates use {{ }} interpolation only, never v-html.

## Testing Guidelines

Place tests in `tests/`, using the same path and module name as the code under test. Name tests with the framework’s conventional suffix, such as `*.test.ts` or `test_*.py`. Every behavior change should include a focused regression test when practical. Run the full configured test command locally before submitting a pull request; report any unavailable or failing checks in the PR description.

A test that needs a scratch folder can take it from `tempDir(prefix)` (`tests/fixtures/temp_dir.ts`), which removes it when the test finishes.

Tests come in three tiers, set in `vitest.config.ts` `tags`, and never pick their own timeout or wait (ESLint rejects `vi.setConfig`, a timeout argument and `vi.waitFor`):

- unit (untagged, 5s): pure logic, stores and components. Await the faked promise and `flushPromises()`; drive timers with `vi.useFakeTimers()`.
- integration (`/** @module-tag integration */` on the file, or `{ tags: ['integration'] }` on a test; 30s): temp repositories, the IPC harness, child processes, file watchers or a full view mount.
- e2e (`{ tags: ['e2e'] }`, 600s): drives uv, python3, cargo, cc, make, perl or Seatbelt end to end; left out by `npm run test:fast`.

State another process or the OS changes is polled with `until()` (`tests/fixtures/until.ts`), whose deadline follows the running test's timeout.

Tests that drive external tools (uv, python3, cargo, cc, make, perl) gate on `hasTools()` from `tests/fixtures/required_tools.ts`: a machine without a tool skips the test, but with `CI` set a missing tool fails the test file. A new tool such a test needs is installed in `ci.yml` at a pinned version.

## Commit & Pull Request Guidelines

Use concise imperative messages, preferably in Conventional Commit form (for example, `feat: add task parser` or `fix: handle empty input`). Pull requests should explain the problem and solution, link related issues, list validation commands and results, and include screenshots or recordings for user-facing changes.

## Security & Configuration

Never commit credentials, tokens, private keys, or machine-specific settings. Add safe defaults to an example file such as `.env.example`, keep real values in local environment files, and document required configuration in the project README as the application develops.
